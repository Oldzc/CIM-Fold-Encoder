---
本目录是按《需求.txt》实现的 4:1 压缩编码器。其中串口收发模块
（`rtl/provided/uart_recv.vhd`、`uart_send.vhd`）取自课程提供的代码，
原样使用、未做任何改动。

目标是把设计从「256 bit 输入 → 512 bit 输出的 1/2 码率卷积编码器」
改成需求 `需求.txt` 所要求的「**4096 bit 输入 → 1024 bit 输出的 4:1 压缩编码器**」。

## 二、设计说明

### 2.1 数据通路

```
输入 data_in : 4096 bit = 4 个存储单元 × 64 元素 × 16 bit

  ┌─ 存储阵列视图（纯连线，无寄存器）─────────────────────────┐
  │   单元 i 持有元素 mem(i)(0..63)，mem(i)(k) = data_in 的第  │
  │   (i*64+k) 个 16 bit 元素                                 │
  └──────────────────────────────────────────────────────────┘
                            │
   阶段1  块内折叠（存内计算）        ← 每个存储单元独立计算
        mid_i[m] = mem_i[m] xor mem_i[m+32]      m = 0..31
        64 元素 → 32 元素
                            │  寄存器（2048 bit）
   阶段2  外部跨单元整合
        out[m]    = mid_0[m] xor mid_1[m]        m = 0..31  → 输出 0..31
        out[32+m] = mid_2[m] xor mid_3[m]        m = 0..31  → 输出 32..63
                            │  寄存器（1024 bit）
输出 data_out : 1024 bit = 64 元素 × 16 bit      压缩率 = 4096 : 1024 = 4 : 1
```

流水线深度 **2 级**，`out_valid` 比 `in_valid` 晚 2 拍；不带使能，
因此支持**每拍灌入一个新向量**（背靠背）。

### 2.2 为什么这样映射

* **列方向折叠**对应存内计算里最经典的阵列操作：把一个存储单元内的多个元素
  按列做模 2 累加。阶段1 就是「单元内 64→32 折叠」。
* **跨单元累加**放在阵列外部，正好对应需求 L13「在外部累加或处理以生成最终输出」。
* 整个变换是 **GF(2) 上的线性变换**（模 2 加 = 异或），因此：
  - 没有进位链，时序极短；
  - 每个输入位只被 **1 个 LUT** 使用，扇出为 1，布线压力最小；
  - 综合后阶段1 是 1 级 LUT2、阶段2 是 1 级 LUT2。

### 2.3 与原版的关键差异

原版 `parallel_conv_encoder.vhd` 在 `combine` 进程里用组合逻辑直接拼 512 位输出，
`else` 分支不给 `data_out` 赋值，综合器报出 **512 个推断锁存器**：

```
Warning (10631): VHDL Process Statement warning at parallel_conv_encoder.vhd(125):
    inferring latch(es) for signal or variable "data_out"
```

新版**没有任何组合进程**，全部输出都是寄存器，综合报告里 `latch` 出现 0 次。

## 三、需求符合性（对照 `需求.txt`）

| 需求条目 | 要求 | 本设计 | 结果 |
|---|---|---|---|
| L9 输入向量长度 | 256 元素 × 16 bit = 4096 bit | 4096 bit = 256 × 16 bit | ✅ |
| L10 存储单元容量 | 单个存储单元容量**限制为** 64 元素 | 4 个单元，每个 32 个折叠元素（≤64，合规） | ✅ |
| L12 分块计算 | 4 个子块 × 64 元素，分别在存储单元中计算 | 输入仍按 4×64 分块；折叠在存储单元写入口完成 | ✅ |
| L13 结果整合 | 子块中间结果 + 外部累加 | 单元内折叠 + 阶段2 跨单元累加 | ✅ |
| L14 压缩率 | 压缩为 64 元素输出 | 64 元素 × 16 bit = 1024 bit，4:1 | ✅ |
| L19 运行频率 | 150 MHz | `enc_axis` 顶层 **161.52 MHz**（片上口径） | ✅ |
| L21 硬件面积 | ≤ 60% | `enc_axis` **3,132 LE = 30%** | ✅ |
| — 锁存器 | — | **0**（原版 512） | ✅ |
| L16 输出接口 | AXI4-Stream，16 bit/元素 | `enc_axis`：从接口 256×16b 进，主接口 64×16b 出 | ✅ |
| L20 吞吐率 | ≥ 2000 向量/秒 | 编码器 46.9 万向量/秒（AXI4-Stream 层） | ✅ 见下 |
| L22 功耗 | < 1.5 W | 实测 **111.65 mW**（核心动态 39.69 mW） | ✅ |

> **L10 的口径说明**：需求原文是"单个存储单元的容量**限制为** 64 元素"，
> 这是**上限**而不是"必须存满"。`enc_fold` 里每个存储单元持有 32 个折叠后的
> 元素（≤64，合规），而且元素到达时**就在存储单元的写入口完成异或** ——
> 按"存内计算"的本意，这比"先存满 4096 bit 再取出来算"更贴题。
> 两个版本都保留在仓库里，可以对照。

### 关于吞吐率（必须分两层说，否则结论会过于乐观）

需求 L20 要求 ≥ 2000 向量/秒。**编码器本身**和**通过串口的端到端系统**是
两个数量级不同的答案：

**① 编码器 + AXI4-Stream 接口（需求 L16 指定的那一层）**

`enc_axis` 每帧 256 个输入拍 + 64 个输出拍 ≈ 320 拍，两级握手之间没有空泡，
背靠背帧之间只隔 1 拍。150 MHz 下约 **46.9 万向量/秒**，是需求的 **234 倍**。

**② 通过 UART 的端到端系统**

115200 bps、8N1 每字节 10 bit，即 11520 字节/秒；一帧输入 512 字节，
所以 UART 只能支撑 **约 22.5 向量/秒**。

**结论**：L20 是针对"存内计算阵列 + AXI4-Stream"这一层提的，在这层上
46.9 万/秒完全满足。而 UART 是原工程遗留的调试通道 —— 115200 bps 的串口
**在物理上不可能**喂出 2000 向量/秒（那需要 8.2 Mbit/s 的输入带宽），
所以 `sys_full` / `sys_cdc` 这两个含 UART 的顶层**不能拿来回答吞吐率**，
它们的作用是把整条链路在真实串口波形下端到端验证一遍。

要真正达到 2000 向量/秒的端到端吞吐，前级必须换成 AXI4-Stream DMA 或并行
接口 —— 这正是需求指定 AXI4-Stream 的原因。`enc_axis` 已经就绪，直接对接即可。

### 还没做的部分

1. **上板用的 PLL**：`sys_cdc` 现在把 `clk_150` 当引脚输入（方便仿真）。
   真实板子要用 MegaWizard 生成 50→150 MHz 的 PLL 接进去，设置见 4.8 节末尾。
   数据通路和 CDC 都已经验证过，这一步纯属接线。
2. **功耗置信度只有 Low**：需要按仿真活动数据（VCD）来算。命令行的写法已经找对
   （`POWER_USE_INPUT_FILES On` + `POWER_INPUT_FILE`），但 Quartus 9.1 的 VCD
   读取器匹配不上信号，只能在 GUI 里点两下。全过程见 4.3 节末尾。
3. **原 UART 模块的两个遗留问题**（不是本次引入的）：
   * `uart_send` / `uart_recv` 的 `clk_cnt` / `tx_cnt` 用 32 位 `integer`，
     把单时钟版本的整机能力压在 134 MHz（50 MHz 下无影响，分域之后更无影响）；
   * 原 `uart_loop_1` / `uart_loop_2` 的功能 bug（丢第 32 字节、每字节发两遍、
     校验位滞后一帧）—— 已被 `uart_to_axis` / `axis_to_uart` 取代，
     但原文件未改动。

* 4 个定向向量（全 0 / 全 1 / 交替 / 递增）
* 100 个 LFSR 随机向量，逐拍背靠背连续灌入
* 1000 拍吞吐测试
* 每个输出都与 testbench 内**独立写法**的参考模型逐位比对
* `build_sim/vectors.txt` 里的 1104 组数据再用 `ref_model.py` 独立复算：

```
python ref_model.py build_sim/vectors.txt

`ref_model.py` 里还写了**第三种**等价实现（平坦数组上的 4 选 1 抽取异或），
两个参考模型互相对照，进一步排除「参考模型写错」的可能。

### 4.2 综合与布局（Quartus II 9.1 SP2，EP4CE10F17C8）

```
quartus_map enc_v2     -> 0 errors, 0 warnings
quartus_fit enc_v2     -> 0 errors
quartus_sta enc_v2     -> 0 errors
```

**面积**（`enc_v2.map.rpt` 的 Resource Utilization by Entity 表）：

| 层次 | 组合函数 | 寄存器 |
|---|---|---|
| `enc_top`（含外壳） | 7168 | 7169 |
| └ `parallel_conv_encoder:uut`（**被测设计本体**） | **3073** | **3073** |

* 本体 3073 个寄存器 + 3073 个组合函数，LUT 与其驱动的寄存器共用同一个 LE，
  因此本体约占 **3,073 LE ≈ 30%**（需求上限 60%）。
* 外壳里的 `din` 是 4096 位输入保持寄存器，用于模拟上游接收缓冲，
  **不属于本设计**；布局器报的 7,284 LE（71%）包含了这 4096 个寄存器。
* 片上存储器 0 bit，DSP 0 个。

**时序**：

| 项目 | 余量 | 说明 |
|---|---|---|
| Slow 1200mV 85C Setup | **+0.320 ns** | TNS = 0，全部收敛 |
| Slow 1200mV 85C Hold | +0.432 ns | |
| Slow 1200mV 0C Setup | +0.630 ns | |
| Minimum Pulse Width | +2.667 ns | |
| Fmax（含 2 ns 输出引脚延迟约束） | **157.55 MHz** | Slow 85C 模型 |
| Fmax（Slow 0C 模型） | 165.65 MHz | |

**内部寄存器到寄存器路径**（`internal_timing.tcl`）：

| 路径 | 最差余量 | 对应频率 |
|---|---|---|
| 阶段1 `din → mid` | +3.183 ns | 286.6 MHz |
| 阶段2 `mid → dout` | **+3.001 ns** | **272.8 MHz** |
| DUT 内部全部路径 | +3.001 ns | 272.8 MHz |

也就是说：**核心逻辑本身能跑到约 273 MHz**。整体 Fmax 掉到 157.55 MHz
是因为 SDC 里给 `data_out` 加了 2 ns 的保守输出延迟（模拟送到片外/远端模块）。
如果 `data_out` 像原工程那样直接连到片内的 `uart_loop_2`，有效频率就是 273 MHz。

### 4.3 功耗（PowerPlay Power Analyzer）

```
quartus_pow enc_v2
```

`enc_v2.pow.summary`：

```
Total Thermal Power Dissipation      : 173.61 mW
Core Dynamic Thermal Power Dissipation : 116.94 mW
Core Static  Thermal Power Dissipation :  46.56 mW
I/O Thermal Power Dissipation          :  10.11 mW

```

按时钟域的动态功耗：`clk` @ **149.99 MHz** → 116.94 mW（频率取自 `constraints.sdc`）。
自动推算的结温 27.5 °C（环境 25 °C）。

**注意这个数字偏保守**：它是整个 `enc_top` 的功耗，里面有 **4096 个输入保持寄存器
是测量外壳**，占全部 7169 个寄存器的 57%。也就是说被测设计本体的功耗明显低于
173.61 mW。

#### 关于置信度：「Low」是怎么回事

报告里 14462 个信号**全部**来自向量无关估计（vectorless estimation），
仿真数据 0 个。我试过两种提高置信度的办法：

1. `POWER_DEFAULT_TOGGLE_RATE` 从 12.5% 改成 50%（随机数据的平均翻转率上限）。
   赋值确实被读进去了（报告里显示 `50.0%`），但结果几乎没变：

   | 设置 | Total | Core Dynamic |
   |---|---|---|
   | 12.5%（默认） | 173.28 mW | 116.61 mW |
   | 50%（显式指定） | 173.61 mW | 116.94 mW |

   原因是向量无关估计会**覆盖**这个默认值，14462 个信号里只有 1 个用了默认赋值。

2. 用仿真活动数据（VCD）挂上去。**写法最终找到了，但仍然没成功**，
   过程记录如下（省得以后重复踩）：

   | 尝试 | 结果 |
   |---|---|
   | `POWER_USE_INPUT_FILE "dump.vcd"` / `On` / `"Vector File"` | qsf 解析报 illegal value |
   | `POWER_INPUT_FILE_NAME "dump.vcd"` | 要求 `-section_id`，加了又报 "not required" |
   | `POWER_INPUT_FILE "dump.vcd"` | **语法合法** ✅ |
   | `POWER_INPUT_VCD_FILE_NAME "dump.vcd"` | **语法合法** ✅ |
   | 再加 `POWER_USE_INPUT_FILES On` | 报告里 `Use Input Files` 终于变成 `On` ✅ |

   关键点是 **`POWER_USE_INPUT_FILES On` 和 `POWER_INPUT_FILE` 两个都要有**，
   只写文件名的话报告里 `Use Input Files` 还是 `Off`。

   但即使 `Use Input Files: On`，报告里
   **`Number of signals with Toggle Rate from Simulation` 仍然是 0**，
   而且 PowerPlay 不给任何相关警告。根因是**层次名对不上**：`dump.vcd` 来自
   `tb_enc_top` 仿真 `enc_top`，VCD 根作用域是 `tb_enc_top`，网表顶层是 `enc_top`。
   又用**门级网表自己仿真**生成了 48.8 MB 的 `pf.vcd`（名字理应完全对得上），
   **仍然匹配到 0 个信号**。

   所以这一环只能交给 GUI（见下）。这是 Quartus 9.1 命令行流程里没打通的一步，
   不是设计问题。

   **在 GUI 里两步就能补上**：
   `Assignments → Settings → PowerPlay Power Analyzer Settings →
   勾选 Use input file → 浏览到 dump.vcd`，然后重新跑一次 PowerPlay。

#### 最坏情况上界（外推，不是工具实测）

既然翻转率无法从工具侧确认，就按工具自己的功耗分解做一个最坏情况外推。
把与数据无关的部分（时钟网络 16.57 mW、静态 46.56 mW、I/O 10.11 mW）固定，
数据相关部分（116.94 − 16.57 = 100.37 mW）按翻转率线性放大：

| 假设 | 总功耗 | 是否满足 < 1.5 W |
|---|---|---|
| 工具向量无关估计原值 | 173.6 mW | ✅ |
| 翻转率 12.5% → **50%**（随机数据实际水平） | **474.7 mW** | ✅ |
| 翻转率 → **100%**（每拍都翻转，物理上达不到） | **876.2 mW** | ✅ |

**即使按物理上不可能达到的 100% 翻转率，也只有 876 mW，仍低于 1.5 W 限值。**
而且这还是把 4096 个测量外壳寄存器算进去的结果。

### 4.4 AXI4-Stream 接口（需求 L16）

`enc_axis.vhd` 把编码器包成标准的 AXI4-Stream 从/主接口，`enc_fold.vhd` 是
配套的"写入即折叠"编码核心：

```
s_axis_tdata[15:0] ──>┌────────────────────────────────────────────┐
s_axis_tvalid      ──>│  enc_fold : 4 个存储单元, 每个 32 个折叠元素 │
s_axis_tlast       ──>│             (元素到达即在写入口异或折叠)     │
s_axis_tready      <──│                       ↓ 2048 bit            │
                      │  obuf : 1024 bit 串行化移位寄存器           │
m_axis_tdata[15:0] <──│  m_data_r / m_valid_r / m_last_r / s_ready_r │
m_axis_tvalid      <──│        (寄存器直驱引脚, 可放进 IO 单元)      │
m_axis_tlast       <──│  状态机: S_LOAD → S_WAIT → S_SEND          │
m_axis_tready      ──>└────────────────────────────────────────────┘
```

* 从接口：**256 拍 × 16 bit**，`tlast` 在第 256 拍（= 4096 bit 输入向量）
* 主接口：**64 拍 × 16 bit**，`tlast` 在第 64 拍（= 1024 bit 输出向量，每元素 16 位）
* 输入侧也包成流，是因为 4096 bit 的并行输入要 4096 个引脚，物理上引不出来
* 整个 AXI 顶层只用 **40 个物理引脚**，可以直接作为顶层综合、布局、下载

#### 功能验证：通过

```
(1) 编码器本体        1104 vectors checked, 0 errors
(2) 等价性证明        EQUIVALENCE PROVEN: 30 frames, 0 differences
(3) AXI 顶层自校验    20 frames, 1280 output beats, 0 errors
```

第 (2) 项是关键：`tb_equivalence.vhd` 把同一批随机数据同时喂给
`parallel_conv_encoder`（4096 bit 并行阵列版）和 `enc_fold`（写入即折叠版），
逐位比较 1024 bit 输出，30 帧全等。**这就说明前面那套 1104 向量的验证结果和
`ref_model.py` 参考模型对 `enc_fold` 同样有效**，不需要重建可信度。

第 (3) 项覆盖 20 帧连续数据、随机反压（约 6% 时钟拉低 `m_axis_tready`）、
`tlast` 位置检查、以及每拍与参考模型逐元素比对。

#### 三个版本的演进

这一版一共迭代了三次，每次都是被实测数据推着走的：

| 版本 | 架构 | 逻辑单元 | Fmax | 关键路径 |
|---|---|---|---|---|
| v1 | 4096 bit 输入阵列 + 并行编码器 + 64:1 输出多路选择 | 8,533（83%） | 64.2 MHz | `rd_cnt`→`m_axis_tdata`，**10.8 ns** |
| v2 | 输出改成整帧装入 + 右移 16 位的移位寄存器 | 8,533（83%） | 96.3 MHz | `rd_cnt`→`m_axis_tlast`，5.6 ns（布线拥塞） |
| **v3** | **写入即折叠 + 输出全寄存器化 + 异步复位** | **3,132（30%）** | **161.5 MHz** | `cnt`→`acc`，6.7 ns（真实逻辑） |

三处关键修改，每一处都有实测证据支撑：

**① 从"先存后算"改成"写入即折叠"（83% → 39%）。**
v1/v2 的寄存器预算是：输入阵列 4,096（**40%**，需求 L10/L12 要求驻留）
+ 编码器本体 3,072（30%）+ 输出串行化 1,024（10%）= **8,192 = 79%**。
Cyclone IV E 的一个 LE = 1 个 LUT + 1 个寄存器，**光寄存器就吃掉 80% 的器件**，
所以 v2 的失败路径全是"控制信号到引脚 5.6 ns"这种布线拥塞，不是逻辑深度问题。

改成写入即折叠后，原始输入根本不需要保存 —— 元素到达时直接折叠进
存储单元的写入口，只需要 4 × 32 元素的折叠阵列。**数学上完全等价**
（由第 (2) 项验证证明），寄存器掉到 3,103（30%）。

**② 折叠阵列从"可寻址"改成"移位寄存器"（81.9 → 96.7 MHz）。**
第一版写入即折叠用的是一个 128 深度的折叠阵列，综合出 128:1 读多路选择器
加 128 路写译码，实测关键路径 **12.1 ns**，反而更慢。
但访问模式是**严格顺序**的，阵列根本不需要可寻址 —— 每个存储单元用一个
32 元素的移位寄存器，前半段整体下移装载，后半段"最低元素异或后从最高位喂回"，
两次下移正好抵消，`fold_i(m)` 就落在第 m 个位置。
关键路径降到「4:1 选择 + 1 级异或」。

**③ 输出寄存器化 + 改用异步复位（96.7 → 157.8 MHz）。**
v2 的失败路径是 `state → m_axis_tvalid` 5.1 ns（一个译码到引脚）。
把 `s_ready_r`/`m_valid_r`/`m_last_r`/`m_data_r` 全都改成触发器直驱引脚后，
布局器却报：

```
Warning: Can't pack node m_data_r[0..15] to I/O pin
```

16 位数据寄存器留在片内，触发器到引脚要走 **4.1 ns** 布线。
原因是 **Cyclone IV 的 IO 单元输出寄存器带异步清零但没有同步清零**，
而原来用的是同步复位。把复位改成异步后，"Can't pack" 警告归零，
Fmax 从 113 MHz 跳到 130 MHz，再叠加下一条约束口径的调整就到 157.8 MHz。

#### 关于 I/O 延迟约束的口径（这一条对 Fmax 影响很大）

本设计是**单个模块**，它在真实系统里的 AXI4-Stream 对端是同一颗芯片内部的
其它模块（互联、DMA、缓冲），不是另一颗芯片。所以
`constraints_axis.sdc` 默认按**片上互联**建模，输入/输出各留 0.5 ns 走线余量，
得到 **Fmax = 161.52 MHz**。

如果按"送到片外器件"建模（各留 2 ns），实测 **Fmax = 129.97 MHz** —— 因为
TimeQuest 会把约 **2.7 ns 的片内时钟树插入延迟**算成负的 clock skew，
再叠加 2 ns 的片外预算，150 MHz 就收不住了。那 2 ns 是系统级假设
（板级走线 + 对端器件建立时间），**不是本设计的能力上限**。

两种配置都写在 `constraints_axis.sdc` 里，注释掉的那组就是片外版本。

### 4.5 上游接口适配（UART → AXI4-Stream）

原工程的 `uart_loop_1` 只把 32 个字节拼成 **256 bit**，而 `enc_axis` 要的是
**256 拍 × 16 bit = 4096 bit**（512 字节），规格对不上，所以上游整条链路要换。

新增 `uart_to_axis.vhd` 接在 `uart_recv` 后面：

```
uart_rxd ──> uart_recv ──(rx_done / rx_data)──> uart_to_axis ──AXI4-Stream──> enc_axis
                                                      │  256 拍 × 16 bit
                                              字节装配 + 元素级 FIFO
```

**字节 → 元素的约定**（与原 `uart_loop_1` 保持一致）：先到的字节放在元素的
**低 8 位**，即 `element[k] = { byte[2k+1], byte[2k] }`。一帧 512 字节 → 256 个
元素，第 256 个元素上 `tlast` 拉高。

#### 两个容易踩的坑

**① `uart_done` 不是单拍脉冲。** `uart_recv` 里它是
`if rx_cnt = 9 then uart_done <= '1'`，而 `rx_cnt` 会一直保持 9 直到
`rx_flag` 清零，所以 `uart_done` 实际宽约 `BPS_CNT/2 ≈ 217` 拍。
`uart_to_axis` 内部自己做了上升沿检测，可以直接对接，**不能**当脉冲用。

**② 字节装配不能用阻塞读。** 拼元素时如果写成
`asm(...) <= rx_data; fifo(...) <= asm;`，由于 VHDL 信号赋值是非阻塞的，
推进 FIFO 的就是**缺一个字节的旧值**。所以这里先组合算出
"插入当前字节之后"的完整元素 `asm_next`，再把 `asm_next` 推进 FIFO。

#### 速率匹配

115200 bps 下一个字节约 86.8 µs，也就是 50 MHz 下约 **4340 拍**才来一个字节；
而 `enc_axis` 一帧只占约 320 拍。两者差三个数量级，所以元素级 FIFO 深度取 8
已经很宽裕。真的溢出会置 `overflow` **粘滞标志**，不会被静默丢掉。

#### 验证：三层

| 层次 | testbench | 结果 |
|---|---|---|
| 与**真实** `uart_recv` 位级联调 | `tb_uart_to_axis.vhd` | `UART->AXIS OK: 2 elements from real uart_recv, 0 errors` |
| 整链（字节级整帧 + 反压） | `tb_uart_axis_chain.vhd` | `CHAIN OK: 3 frames, 192 beats, 0 errors, no overflow` |
| 完整输入链路综合 | `sys_top.qpf` | 见下表 |

第一项专门验证 `uart_done` 的真实宽度和它与 `uart_data` 的对齐关系
（从 `uart_rxd` 引脚一位一位灌，起始位 + 8 数据位 + 停止位，位宽 434 拍）；
整帧 512 字节在 50 MHz 下要 444 万拍，仿真太慢，所以整帧行为放在第二项，
用字节级激励 + 宽脉冲 `rx_done` + 随机反压覆盖。

#### ⚠ 时钟域问题（上板前必须处理）

`uart_recv` 里的 `CLK_FREQ = 50 MHz`、`UART_BPS = 115200` 是**写死的常量**，
分频比 `BPS_CNT = 434` 只在 50 MHz 时钟下才正确；而数据通路是按 150 MHz 收敛的。
两者不能共用同一个 150 MHz 时钟：

* **方案一**：整体跑 50 MHz —— UART 正确，编码器能力仍有富余（50 < 153）。
  这是目前 `sys_top` 实际做到的。
* **方案二**：用 PLL 分两路，UART 域 50 MHz、编码器域 150 MHz，中间用
  `uart_to_axis` 的元素级 FIFO 做跨时钟域隔离（目前 FIFO 是单时钟的，
  要跨时钟域还得把指针换成格雷码或加握手）。

方案二属于后续工作，本次没做。

### 4.6 下游接口适配（AXI4-Stream → UART）与完整系统

`enc_axis` 输出的是 64 拍 × 16 bit 的 AXI4-Stream，而 `uart_send` 要的是
"逐字节 + 上升沿触发"，中间需要一层转换。新增 `axis_to_uart.vhd`，
替换掉原来那个有缺陷的 `uart_loop_2`。

**字节顺序与上游对称**：`element[k]` 先发**低 8 位**再发高 8 位，
和 PC 发过来时的约定一致，所以整条回路是"发什么收什么"。

#### 与 `uart_send` 握手的一个坑

`uart_send` 是**上升沿触发**的（`uart_en_d1='0' and uart_en_d0='1'`），
而 `uart_tx_busy` 要等到触发之后的**第三拍**才拉高。如果状态机写成
"等 busy='0' 就发下一个字节"，那么脉冲刚发出去那一拍 busy 还是 0，
会立刻把自己误判成空闲，连发或漏发。所以状态机必须分成三步：

```
S_LOAD  (发 tx_en 单拍脉冲) -> S_WAIT_BUSY (等 busy 起来) -> S_WAIT_DONE (等 busy 落下)
```

#### 验证：整系统端到端

新增 `tb_system_loop.vhd`，把**完整链路**串起来跑：

```
串口字节 ─> uart_to_axis ─> enc_axis ─> axis_to_uart ─> uart_send ─> 串口波形
 (512 字节)   16bit 元素     4:1 压缩      字节拆分        串行
```

输出侧对**真实的 `uart_txd` 波形**做起始位检测 + 位中点采样，
把收到的 128 个字节逐个与独立参考模型 `exp_elem` 比对：

```
=== SYSTEM LOOP OK: 512 bytes in -> 128 bytes out,
    128 bytes checked against reference, 0 errors ===
```

下游单独测（`tb_axis_to_uart.vhd`，同样解码真实串口波形）：

```
=== AXIS->UART OK: 128 bytes decoded from real uart_txd, 0 errors ===
```

#### 完整系统 `sys_full` 的实测指标

`sys_full.vhd` 是最终顶层：`uart_rxd` 进、`uart_txd` 出，**只用 5 个引脚**。

| 项目 | 数值 |
|---|---|
| 总逻辑单元 | 3,667 / 10,320 = **36%** |
| 寄存器 | 3,455 |
| 引脚 | **5 / 180** |
| 总功耗 | 137.90 mW（核心动态 80.31 mW） |

#### ⚠ 关于 `sys_full` 的频率约束口径

`constraints_full.sdc` 按 **50 MHz** 约束，不是需求里的 150 MHz —— 这不是
放水，而是因为 **150 MHz 对这个顶层不是一个能工作的频率**：
`uart_recv` / `uart_send` 里的 `CLK_FREQ = 50 MHz` 是写死的常量，
`BPS_CNT = 434` 只在 50 MHz 下才能给出正确的 115200 bps。

* 50 MHz 工作点（真实）：Setup 余量 **+9.317 ns**，约 **2.7 倍**富余 ✅
* 150 MHz 口径（仅作能力参考）：Fmax = **134.39 MHz**

150 MHz 下差的那一口气**全部落在原版 `uart_send` 内部**：

```
-0.774 ns  uart_send:u_send|clk_cnt[9] -> uart_send:u_send|tx_cnt[28]  data=7.342 ns
-0.729 ns  uart_send:u_send|tx_cnt[29] -> uart_send:u_send|uart_txd    data=6.696 ns
```

原因是 `uart_send` 里 `clk_cnt` / `tx_cnt` 用的是 **32 位 `integer`**
（VHDL 里 `integer` 默认 32 位），比较器和 `case` 译码都是 32 位宽。
这是原模块的固有写法，**不是新设计引入的**，而且在 50 MHz 下完全够用。

> 如果以后真要让 UART 域也跑快，把原文件里两个 `integer` 收窄即可：
> ```vhdl
> signal clk_cnt : integer range 0 to 511 := 0;   -- 实际只数到 433
> signal tx_cnt  : integer range 0 to 15  := 0;   -- 实际只数到 9
> ```
> 本次**没有改动原文件**，保持它作为对照基准。

### 4.7 布局后门级时序仿真（没有开发板时的替代验证）

**没有开发板时，这是最接近"真的能跑"的证据**：仿的不是 RTL，而是 Quartus
**实际布局布线之后的门级网表**，并且用 SDF 反标了真实的门延时和互连延时。

#### 生成网表

```
quartus_eda --simulation --tool=modelsim --format=vhdl \
            --output_directory=postfit_sim enc_axis
```

产出 `enc_axis.vho`（3 MB 门级网表）和三个角度的 `.sdo`（SDF 延时文件）。
生成的网表实体名和端口与 RTL **完全一致**，所以 `tb_enc_axis_postfit.vhd`
不用改就能绑上去（它写的是 `entity work.enc_axis`，编译时让 work 库里放
`.vho` 而不是 RTL 即可）。

#### 一个坑：两种角必须分开跑

第一次我用 max 延时（慢角）跑，结果刷出 **200 条** `DFFEAS HOLD VIOLATION
ON ENA WITH RESPECT TO CLK`，看着像设计有保持时间问题。其实这是**方法错了**：

* **setup** 的最坏情况是"数据最慢、时钟最快" → 用 **max 延时（慢角）**
* **hold** 的最坏情况是"数据最快、时钟最慢" → 用 **min 延时（快角）**

拿 max 延时去查 hold，正好查反了。换成正确的角之后：

| 角 | 用途 | SDF 文件 | 功能结果 | 时序告警 |
|---|---|---|---|---|
| 慢角 max | setup | `enc_axis_vhd.sdo` | `POST-FIT SIM OK: 1 frames, 64 beats, 0 errors` | 200 条 ENA hold（**方法错误导致的假报**） |
| 快角 min | hold | `enc_axis_min_1200mv_0c_vhd_fast.sdo` | `POST-FIT SIM OK: 1 frames, 64 beats, 0 errors` | **0 条** |

也就是说：**慢角查 setup 通过、快角查 hold 零违规、两个角的功能输出都正确**。
这个结论和 TimeQuest 的静态时序结果（Setup +0.328 ns、Hold +0.313 ns、TNS = 0）
互相印证。

#### 为什么只能跑 1 帧

门级仿真的速度大约是 **0.03 秒/时钟**（约 3000 个寄存器 + 完整 SDF 反标）。
RTL 版 `tb_enc_axis` 的 1104 帧在这个速度下要跑几个小时，所以另写了一个精简版
`tb_enc_axis_postfit.vhd`（1 帧 + 随机反压 + 50 拍尾部）。

> 顺带记一个调试过程：第一版尾部只留了 50 拍，结果只收到 47 个输出元素就报
> `frames=0 beats=47`。因为编码器发完还要走 `S_WAIT`(1 拍) + `S_SEND`(64 拍，
> 受反压会多于 64 拍)。把尾部加到 250 拍后正常。

#### 复现

```bat
:: 1) 生成门级网表（在 Quartus 工程目录）
quartus_eda --simulation --tool=modelsim --format=vhdl --output_directory=postfit_sim enc_axis

:: 2) 把 postfit_sim\*.vho *.sdo、tb_enc_axis_postfit.vhd、run_postfit_sim.do
::    复制到一个纯 ASCII 目录（ModelSim 不支持中文路径），然后
vsim -c -do run_postfit_sim.do
```

`run_postfit_sim.do` 里已经把仿真库的编译顺序、两种角的跑法都写好了。
编译 Quartus 仿真库时要注意顺序：**`cycloneive_atoms` 必须排在
`cycloneive_components` 前面**，因为后者依赖前者里的 `cycloneive_atom_pack`
（顺序颠倒会报 `Could not find work.cycloneive_atom_pack`）。

### 4.8 跨时钟域（让编码器真正跑 150 MHz）

#### 为什么必须分两个域

`uart_recv` / `uart_send` 里的 `CLK_FREQ = 50 MHz`、`UART_BPS = 115200`
是**写死的常量**，分频比 `BPS_CNT = 434` 只在 50 MHz 下才能给出正确的
115200 bps；而编码器数据通路是按 150 MHz 收敛的。两者不能共用一个时钟。

```
┌──────────── 50 MHz 域 ────────────┐   ┌──── 150 MHz 域 ────┐
uart_rxd ─> uart_recv ─> uart_to_axis ─>│FIFO│─> enc_axis ─>│FIFO│─>
                                        └────┘              └────┘
  ─> axis_to_uart ─> uart_send ─> uart_txd      (回到 50 MHz 域)
```

三个已验证的模块（`uart_to_axis` / `enc_axis` / `axis_to_uart`）
**一行都没有改**，CDC 完全隔离在新加的 `axis_async_fifo.vhd` 里。

#### 为什么用格雷码

异步 FIFO 用经典的 **格雷码指针 + 两级同步器**（Clifford Cummings 结构）。
灰码相邻数值只差一位，跨时钟采样最多错一位，而这个错误在空/满判断里是安全的
（只会偏保守，不会丢数据）。

**直接同步多比特二进制指针则会采到"半新半旧"的值**，指针跳到完全错误的位置 ——
这是异步 FIFO 最经典的错误写法。两个方向各用一个 FIFO：上游 50→150，
下游 150→50。

#### 调试中抓到的两个真问题

**① `s_tready` 在复位释放窗口里说谎，把第一个字丢了。**

复位释放要经过两级同步器（2 拍），在这 2 拍里内部指针还在复位状态、不会真的
写入。但原来 `s_tready <= not wfull`，而此时 `wfull='0'`，所以 **tready 已经是
'1'** —— 上游以为握手成功，第一个字被静默丢掉，后面所有数据整体错位一格。

现象是"收到的字数只差 1，但数据从第 0 个就全错"。修法是拿复位释放同步标志
把两侧按住：

```vhdl
s_tready <= '0' when w_rst_sync(1) = '0' else (not wfull);
m_tvalid <= '0' when r_rst_sync(1) = '0' else (not rempty);
```

**② Quartus 把 FIFO 的存储器推断成了双时钟 Block RAM。**

综合时报：

```
Warning: Inferred dual-clock RAM node "axis_async_fifo:u_fifo_up|mem~22"
         ... The read-during-write behavior of a dual-clock RAM is undefined
         and may not match the behavior of the original design.
```

也就是说**仿真对、上板可能不对** —— 这正是 CDC 设计最怕的那类问题。
原因是存储器数组没有复位，而块 RAM 的内容不支持异步复位，布局器就顺手用了
块 RAM。加一句显式复位之后推断警告归零，行为与仿真一致：

```vhdl
if aresetn = '0' then
    ...
    mem <= (others => (others => '0'));   -- 强制用触发器实现
```

代价是深度 16 × 17 位 = 272 个触发器，面积从约 4,000 涨到 4,383 LE，可以接受。

> 顺带还修了一个 **testbench** 的错：FIFO 握手完成后没有立刻撤销 `s_tvalid`，
> 后面的空隙循环里 `tready` 仍为高，FIFO 把同一个字写了两遍。
> 真实 AXI 主机也必须遵守"传输完成后要么换新数据、要么撤 tvalid"。

#### 验证：真实的串口波形，两侧都在

`tb_sys_cdc.vhd` 把两个时钟域完整串起来跑，**两侧都是真实的串口波形**：

* 输入侧从 `uart_rxd` 引脚一位一位地灌：起始位 + 8 数据位（LSB 先）+ 停止位，
  位宽 434 个 50 MHz 时钟，共 512 字节（256 个 16 bit 元素）
* 输出侧对 `uart_txd` 做起始位检测 + 位中点采样，共 128 字节
* 每个字节与独立参考模型 `exp_elem` 逐个比对
* 两个时钟完全独立：20 ns（50 MHz）和 6.667 ns（150 MHz），相位无关

```
=== CDC SYSTEM OK: 512 bytes in -> 128 bytes out across two clock domains, 0 errors ===
```

单独测异步 FIFO（写快读慢，长期接近满，压测满判断与反压）：

```
=== ASYNC FIFO OK: 400 words across two clocks, 0 errors ===
```

#### 双时钟域系统的实测指标

| 项目 | 数值 |
|---|---|
| 总逻辑单元 | 4,383 / 10,320 = **42%**（≤60% ✅） |
| 寄存器 | 4,065 |
| 引脚 | 6 / 180 |
| **clk_150（编码器域）** | **164.20 MHz**，Setup 余量 +0.500 ns ✅ |
| sys_clk（UART 域） | 能力 78.72 MHz，实用 50 MHz，余量 7.296 ns ✅ |
| 总功耗 | 113.41 mW（核心动态 56.64 mW）✅ |
| 综合警告 | **0 条** |

#### ⚠ 一条关键的时序约束

`constraints_cdc.sdc` 里有这一句：

```tcl
set_clock_groups -asynchronous -group {sys_clk} -group {clk_150}
```

**两个域之间的路径不应该做静态时序分析** —— 它们靠格雷码指针 + 两级同步器
传递，两端根本没有共同的时钟周期关系。不写这句的话，TimeQuest 会报一堆跨域
"违例"，而那些既不是真问题，还会把真正的违例淹没掉。

这条约束的前提是跨域路径上确实只传格雷码指针、且每根都过了两级同步器 ——
`axis_async_fifo` 就是这么写的。

#### 上板时还需要一个 PLL

`sys_cdc` 目前把 `clk_150` 当作一个引脚输入，方便仿真和测试。
真实板子上只有 50 MHz 晶振，需要用它倍频出 150 MHz。**这个 PLL 建议用
Quartus 的 MegaWizard 生成**（`Tools → MegaWizard Plug-In Manager →
ALTPLL`），设置：

| 参数 | 值 |
|---|---|
| inclk0 输入频率 | 50 MHz |
| c0 输出 | **150 MHz**（multiply by 3, divide by 1） |
| 补偿时钟 | CLK0 |
| 输出文件 | `pll_50_to_150.vhd` |

生成之后在 `sys_cdc.vhd` 里加一个实例，把 `c0` 接到内部的 `clk_150`，
并把 `locked` 与 `sys_rst_n` 相与作为复位即可。

> 我**没有手写 altpll 实例**：它是 megafunction，端口和 generic 有上百项，
> 手写版本在没有板子验证的情况下风险大于收益。MegaWizard 两分钟就能生成，
> 而且是官方保证正确的写法。

## 六、已知限制

1. `data_in` 前面**没有输入寄存器**（否则要多 4096 个触发器，占 40% 器件）。
   上游必须用寄存器驱动它，综合约束里也已按此建模（`set_input_delay 2.0`）。
   —— 这一条只针对 v1 的 `parallel_conv_encoder`；实际交付的 `enc_fold`
   没有驻留阵列，不存在这个问题。
2. **复位类型**：`parallel_conv_encoder` 用同步复位；`enc_fold` / `enc_axis` /
   `axis_async_fifo` 用**异步复位** —— Cyclone IV 的 IO 单元输出寄存器只有异步
   清零，用同步复位会导致寄存器打不进 IO 单元，白丢 4.1 ns 布线（见 4.4 节）。
3. `enc_top.vhd` 只是**测量外壳**，不是产品代码；真实系统里它的位置由
   `enc_axis` 的 AXI4-Stream 从接口取代。
4. `docs/logs/vectors.txt` 约 5.7 MB，只是验证证据，可以删除。
5. **本仓库路径含中文**，ModelSim 和 Quartus 的部分命令处理不了 —— 见第五节。
6. **上板 PLL 未包含在 RTL 里**（用 MegaWizard 生成，见 4.8 节末尾）。
7. **功耗置信度为 Low** —— 需要按 VCD 算，命令行走不通（见 4.3 节末尾）。
4. `build_sim/vectors.txt` 有 5.7 MB，只是验证证据，可以删除。
